# 新书创作架构向导与纵横叙事引擎的关系

## 1. 一句话定位

**新书创作架构向导负责“把一本还没有开始运行的小说建模出来”；纵横叙事引擎负责“让这套模型在几十万到百万字的生产过程中持续运行、审计、更新和呈现”。**

因此二者是上下游关系，不是替代关系。

---

## 2. 为什么从纵横项目中抽出一个独立 Skill

纵横叙事引擎是一套完整小说生产协议，关注的不只是“第一次把设定想清楚”，还包括：

- 中程剧情合约；
- 多角色行动推演；
- 事实、逻辑与 OOC 审计；
- 正式真值持久化；
- 状态更新；
- 伏笔资产生命周期；
- 失败回滚与质量控制；
- 正文文学呈现。

但在进入这些环节之前，有一个更上游的问题：

> **作者脑中的灵感，怎样变成足够稳定、彼此有因果关系、可以进入工程系统的初始事实？**

这就是本 Skill 单独解决的问题。

它允许作者不运行完整纵横软件，也能在一个普通强模型 / Agent / Codex 会话中完成新书架构。

---

## 3. 两套系统的边界

### 新书创作架构向导负责

```text
模糊创意
  ↓
发现真正创作意图
  ↓
建立题材与读者承诺
  ↓
世界产生压力
  ↓
人物产生选择
  ↓
建立关系与知识边界
  ↓
形成持续冲突
  ↓
构造一个开书核心初始剧情段
  ↓
健康检查
  ↓
确认新书核心事实
```

### 纵横叙事引擎继续负责

```text
确认的新书核心事实
  ↓
正式数据初始化
  ↓
L1A / 中程剧情合约
  ↓
多角色基于本体、信息盲区和资源进行推演
  ↓
导演收束
  ↓
客观审计
  ↓
正式真值回写
  ↓
资产与状态生命周期
  ↓
文学呈现
  ↓
下一叙事单元
```

## 4. 概念映射

| 新书 Skill | 纵横体系中的后续用途 | 说明 |
|---|---|---|
| 创作动机 | 全书价值与方向约束 | 防止后续“技术上合理、但已经不是作者想写的书” |
| 核心创新 | 长期差异化承诺 | 不是一句宣传语，而要能影响世界、人物或冲突 |
| 核心卖点 | 长期兑现目标 | 后续剧情应反复用不同形式兑现，而非开篇一次性消费 |
| 防雷 / 负面清单 | 负向约束源 | 给后续合约、审计和质量控制提供“绝不能发生什么”的上游依据 |
| 世界规则 | 世界真值初始化素材 | 后续需要转为更严格的系统事实和状态 |
| 地理 / 资源 / 势力 | 世界运行结构 | 决定谁能做什么、争什么以及代价从哪里产生 |
| 职业 / 能力体系 | 角色能力与代价基础 | 强能力必须有边界，否则无法形成可靠推演 |
| 怪物 / 灾难 / 非人格化威胁 | 外部压力源 | 可以承担主要对立力量，不要求强行人格化反派 |
| 关键历史 | 当前世界状态的因果来源 | 历史的价值在于给“现在”留下后果 |
| 人物底盘 | 角色本体初始化 | 用人类可读方式表达稳定性格、价值排序、底线 |
| 欲望 / 恐惧 / 动机 | 角色行动驱动 | 后续推演需要回答“为什么这个人此刻会这么做” |
| 能力 / 资源 / 限制 | 行动可供性 | 决定角色能做什么，以及做了要付什么 |
| 知识边界 | 信息盲区初始化 | 区分知道、不知道、误信和怀疑，防止角色获得作者视角 |
| 重要关系 | 角色间作用力 | 不是人物通讯录，而是会改变选择的关系 |
| 冲突种子 | 后续合约候选矛盾 | 要能持续、升级，并且不能靠一次解释轻易消失 |
| 开书核心初始剧情段 | 初始 L1A 的业务素材 | 定义触发、升级、代价、不可逆后果与信息揭露边界 |
| 阶段事实卡 | 正式入库前的人类确认层 | 防止对话过程中已确认事实衰减 |
| 健康度闸门 | 正式工程流程前的软审计 | 不替代引擎运行期的客观审计与硬约束 |

## 5. 为什么 Skill 不直接输出数据库字段

独立 Skill 面向的是普通作者和通用强模型。

如果在交互阶段就要求作者理解：

- 数据表；
- JSON 合同；
- 角色数值维度；
- RPC；
- 状态机；
- 数据库存储原子；

作者的注意力会从“我到底想写一本什么书”转移到“我要怎么正确填软件”。

因此本 Skill 有意保持**业务语义层**：

> 作者用创作语言确认事实，软件负责把事实映射成自己的运行结构。

这也让 Skill 可以脱离纵横软件单独使用。

---

## 6. “阶段事实卡”与“真值层”不是一回事

这是最容易混淆的地方。

### 阶段事实卡

是：

- 用户已经确认；
- 当前对话不应再随意改变；
- 最终文档应从这里重组；

它是**创作交互层的 Canon**。

### 纵横真值层

是：

- 正式进入运行系统；
- 具备明确数据合同；
- 状态变更受到约束；
- 审计失败可以拒绝写入或回滚；

它是**生产运行层的 Canon**。

Skill 的事实卡降低“进入真值层之前就已经说乱”的概率，但不能提供数据库级一致性保障。

---

## 7. “健康度检查”与“正式审计”也不是一回事

Skill 的健康度检查关注：

- 新书字段是否完整且有效；
- 卖点和题材承诺是否成立；
- 世界是否真的制造压力；
- 人物是否会主动做选择；
- 设定、角色和开书剧情是否互相支持；
- 是否违反作者明确防雷；
- 是否存在明显的故事发动机故障。

这是**架构审查**。

纵横引擎后续审计发生在实际叙事运行中，还需要检查：

- 当前正式事实；
- 人物知识边界；
- 状态变化；
- 行为可行性；
- OOC；
- 合约要求；
- 数据一致性；
- 是否允许正式回写。

这是**运行时审计**。

---

## 8. 为什么只生成一个“开书核心初始剧情段”

新书阶段需要证明故事发动机能启动，但不应该过早把整部小说锁死。

因此本 Skill 只要求一个完整开书核心事件：

- 谁在什么地方；
- 为什么现在发生；
- 各自想得到什么；
- 冲突如何升级；
- 失败代价是什么；
- 发生了什么不可逆后果；
- 哪些信息被揭露，哪些仍然隐藏；
- 事件结束后留下什么长期压力。

它的作用是：

> **用一个可以落地的事件，验证创作原点、世界、人物和冲突是否真的能协同运行。**

未来的中程剧情应由后续叙事运行继续产生，而不是在新书初始化阶段预编几十个 L1A。

---

## 9. 独立使用与接入纵横

### 独立使用

作者可以：

```text
SKILL.md
   ↓
强模型 / Agent
   ↓
多轮架构对话
   ↓
《新书核心设定》
```

然后把结果用于任何写作流程。

### 接入纵横

理想链路是：

```text
SKILL.md
   ↓
作者确认的新书核心设定
   ↓
纵横新书创建流程
   ↓
业务字段 / 真值初始化
   ↓
首个 L1A
   ↓
正式生产管线
```

因此，Skill 的最终输出应该尽量保持：

- 完整；
- 明确；
- 无占位符；
- 无内部矛盾；
- 可追溯到作者确认；
- 不包含大量软件无关的百科信息。

---

## 10. 核心设计哲学的一致性

两者虽然处于不同层级，但共享同一个基本判断：

> **小说不是“AI 连续写很多字”的结果，而是角色在有规则的世界里，因为知道什么、不知道什么、想要什么、害怕什么、能够做什么，而不断做出有代价的选择。**

新书 Skill 负责把这套初始条件建立起来。

纵横叙事引擎负责让这些条件在长篇生产中持续成为真实约束。
